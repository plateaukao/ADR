# Stripping inline script/style from translation units

## What was broken

On `news.yahoo.co.jp`, the bilingual translation output was garbage: chunks of
raw JavaScript were being translated, producing nonsense lines next to the real
article. I reproduced and confirmed this live over the Chrome DevTools Protocol
(CDP) against the actual rendered DOM of a real Yahoo article — **7 translation
units were leaking JavaScript/CSS source** such as `window.msthdPromo=…`,
`YAHOO.JP.templa.EMG.refresh=function(){…}`, and `window.ualcmds=…`.

## Root cause

Yahoo (like many portals) wraps tracking and promo `<script>` tags — and the
occasional inline `<style>` — inside bare `<div>`s that contain **no
block-level children**. The scanner's `walk()` therefore treated each such
`<div>` as a *leaf translation unit*.

The unit's translatable text comes from `unitText()`, which iterated the
element's child nodes and skipped only `BLOCK_TAGS` (each block child is its own
unit) plus our own injected wrappers. It never consulted `EXCLUDE_TAGS`. A
`<script>` is not a block tag, so the function fell through to
`t += node.textContent` and happily appended the entire JavaScript source as
"translatable text." `segText()` (used when a `<div>` body is split into
`<br>`-delimited paragraphs) had the identical gap.

`EXCLUDE_TAGS` was only ever honoured at *subtree-descent* boundaries
(`isExcluded`, `walk`, the `closest()` guard) — never at the point where a unit
gathers its own inline text. An inline `<script>` sitting beside visible text
slipped straight through.

```mermaid
flowchart TD
    A[For each child node of a translation unit] --> B{Node type?}
    B -->|Text| KEEP[Append the text]
    B -->|Element| C{Which tag?}
    C -->|BR| SP[Append a space]
    C -->|SCRIPT / STYLE / NOSCRIPT| EX[Skip: invisible source code]
    C -->|imtx wrapper| WR[Skip: our own injected translation]
    C -->|Block tag P, DIV, LI| BL[Skip: it becomes its own unit]
    C -->|Inline a, span, strong| IN[inlineText: recurse, strip excluded subtrees]
    EX -. branch missing before v0.6.1 .-> LEAK[JavaScript source leaked into the text sent to the engine]
    LEAK --> NONSENSE[Nonsense bilingual output on news.yahoo.co.jp]
```

## The fix

Three changes in `immersive-translate-openai.user.js`, all in the scanner:

1. **A recursive `inlineText(node)` helper** that gathers an inline node's
   visible text while *stripping excluded subtrees* (`script`/`style`/… and our
   own `imtx-*` wrappers), collapsing `<br>` to a space. Because it recurses, it
   handles not just a direct inline `<script>` child but the nested case too —
   e.g. `<span>words<script>…</script>more</span>`.

2. **`unitText()` now skips `EXCLUDE_TAGS` inline children outright** and uses
   `inlineText()` for the inline elements it does keep. `segText()` was switched
   to `inlineText()` for the same protection on the `<br>`-split path.

3. **`splitSegments()` gained an `INVISIBLE_TAGS` set**
   (`script/style/noscript/template`). A genuinely zero-width node between two
   text runs is now *skipped* rather than treated as a paragraph break — so
   contiguous visible text on either side of an inline tracking script stays a
   single bilingual unit instead of being split on an invisible boundary. (This
   differs from a *visible* exclude like `IFRAME`/`VIDEO`, which still breaks a
   paragraph.)

A `<div>` whose only content was a script now yields empty `unitText()`, falls
below `minTextLength`, and is dropped from the unit set entirely.

## Verification

Re-running the same CDP probe against the live Yahoo article, before vs after:

| Metric | Before | After |
| --- | --- | --- |
| Translation units found | 316 | 203 |
| Units leaking JS/CSS source | **7** | **0** |
| Real Japanese article paragraphs still collected | — | 97 |

The drop from 316 to 203 units is exactly the bare script-wrapper `<div>`s no
longer qualifying. The real article body (97 Japanese paragraphs — the typhoon
coverage) is untouched.

## A pre-existing test breakage, surfaced and fixed

Wiring up a regression test exposed that the **entire smoke suite had silently
stopped exercising the mock server.** v0.6.0 flipped the default `engine` to
`'google'` (free, keyless), but the GM-shim fixtures only set `apiBaseUrl`/
`apiKeys` and never pinned `engine`. So every fixture had been calling the *real*
Google Translate endpoint and the `【譯】`-prefix assertions were quietly wrong.

Pinning `engine: 'openai'` in the fixtures (`harness.html`, `naver-style.html`,
the new `inline-script.html`; `harness.min.html` is regenerated by the build)
restored deterministic, mock-driven testing. A new `test/pages/inline-script.html`
fixture mirrors Yahoo's structure — a leaf `<div>` with an inline script+style,
a script-only `<div>`, and a paragraph whose inline `<span>` hides a nested
script — guarded by four checks (no JS in any translation, only visible text
translated, script-only div skipped, nested script stripped). Suite is **28/28**
on both the readable and minified builds.

## Notes on tooling

CDP was the key to a confident diagnosis: neither Arc nor Chrome exposes a debug
port unless launched with `--remote-debugging-port`, and an installed extension
(even "Claude for Chrome") cannot grant one to an outside process. Rather than
disrupt the running browser, I launched a **second** headless Chrome with a
throwaway profile (`--remote-debugging-port=9222 --remote-allow-origins=*`),
loaded the exact article, and injected the scanner's own logic via
`Runtime.evaluate` — proving both the leak and the fix against the real DOM
without touching the user's session.
